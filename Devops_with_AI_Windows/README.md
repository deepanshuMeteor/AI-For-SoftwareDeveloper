# AI Driven DevOps with Docker

A hands-on Jupyter notebook lab that teaches engineers how to use Generative AI
(GitHub Copilot + Azure OpenAI) for everyday DevOps work — writing Dockerfiles,
debugging container issues, generating Jenkins pipelines, and producing
Terraform configurations for Azure.

The lab runs entirely on a Windows VM with Docker Desktop and a local Jenkins
installation. There is no live cloud deployment — Terraform commands are
generated and reviewed but not applied, so you can complete the lab without
any cloud spend.

---

## What You Will Learn

By the end of this lab you will be able to:

1. Use GitHub Copilot and Azure OpenAI to design DevOps pipelines
2. Generate production-ready Dockerfiles using AI prompts
3. Debug container issues (CrashLoopBackOff, build errors, OOM) with AI guidance
4. Deploy a microservice locally using AI-generated Docker Compose workflows
5. Automate CI/CD tasks using reusable Jenkins prompt templates
6. Generate and review Terraform configurations for Azure infrastructure
7. Walk through a full development-to-deployment cycle end to end

---

## The Application You Build

The lab uses a small FastAPI service (`app.py`) as the working example. The
focus is not the application itself — it is the DevOps tooling around it. You
containerise it, write a Compose stack for it, generate a Jenkins pipeline that
builds and pushes it, and produce Terraform that would host it on Azure.

This keeps the application surface area small so you can concentrate on the
AI-assisted DevOps workflow rather than application logic.

## Notebook Structure

The notebook is organised into nine sections. Each one has a short markdown
explanation followed by code cells you run in order.

### Section 1 — Introduction and Setup
Verifies Python, Docker, and Git are reachable from the kernel. Installs the
three Python packages used throughout the lab (`openai`, `python-dotenv`,
`requests`) and connects to your Azure OpenAI deployment. Defines the
`ask_ai()` helper that every later section uses.

### Section 2 — Designing DevOps Pipelines with Generative AI
Introduces the structured prompt template (Role, Context, Task, Format) and
uses it to generate a Jenkinsfile. You also ask the AI to explain each stage
of the pipeline so you understand what was generated rather than just copying it.

### Section 3 — Generating a Dockerfile with AI
The AI writes a production-quality Dockerfile for the FastAPI app —
multi-stage build, non-root user, healthcheck, layer ordering for cache
efficiency. Then it generates a `docker-compose.yml` for running the stack
locally.

### Section 4 — Debugging Container Issues with AI
You paste real error output (failed build logs, container crash messages)
into an AI debugging function and get back a root-cause analysis with exact
fix commands. The section uses a deliberately-broken `Dockerfile.broken` as
a reproducible example.

### Section 5 — Deploying Microservices with AI-Generated Workflows
Covers the local deployment path with Docker Compose: bringing the stack up,
running a smoke test against the API, viewing logs, and tearing it down.

### Section 6 — Automating CI/CD with Jenkins Prompt Templates
Builds a reusable pattern for generating Jenkins pipeline stages from prompts.
You learn how to encode standards (lint, build, scan, push, deploy) into
templates that a team can share.

### Section 7 — Terraform Configurations for Production with AI
The AI generates Terraform (`main.tf`, `variables.tf`) for an Azure environment
including a resource group, virtual network, and AKS-ready scaffolding.
The `terraform init / plan / apply` commands are shown for reference but are
not executed inside the notebook.

### Section 8 — End-to-End Walkthrough
Ties everything together: edit code, build the image, run with Compose, push
to the GitHub repository, and trigger the Jenkins pipeline locally to see
the full cycle in one pass.

### Section 9 — Best Practices and Wrap-Up
Summarises the prompting patterns, common pitfalls, and how to extend the
`ask_ai()` workflow into your day-to-day work.

The `.env` file must sit in the same folder as the notebook and contain:

excludes it.

## How to Use This Beyond the Lab

**At work — shipping faster.** Use the prompt templates and `ask_ai()` helper
in your own projects. When you need a Dockerfile for a new service or a
Jenkins stage for a new requirement, describe what you need and get a working
draft in seconds instead of searching documentation for an hour.

**Onboarding new engineers.** The notebook doubles as a training guide. New
engineers can run it end to end and understand how the deployment stack works,
with AI explaining each component along the way.

**Standardising DevOps across teams.** The prompt-template pattern in
Section 6 lets you encode your organisation's standards into reusable
functions. Every team generates consistent Dockerfiles, pipelines, and
Terraform from the same base prompts.

**Incident response.** The debugging workflow in Section 4 (collect evidence,
ask AI, apply fix, verify) works just as well on real production errors as
on the broken Dockerfile in the lab. Paste `docker logs`, `kubectl describe`,
or a Terraform error and get a structured analysis.

**Learning Docker and Terraform.** Every generated file is explained by the
AI in plain language. You can add cells and call `ask_ai()` with your own
follow-up questions at any point.

## Key Concepts Explained Simply

**Prompt template.** A fill-in-the-blank instruction for the AI. Write it
once, fill in the service name or environment each time you use it. Same
quality output every time.

**Multi-stage Docker build.** Building an image in two steps: one compiles or
installs everything, the second copies only what is needed to run. The final
image is much smaller and contains no build tools that could be a security risk.

**CrashLoopBackOff.** A container that keeps failing on startup so the
orchestrator keeps restarting it. Usually caused by a missing environment
variable, a bad config, or a dependent service not being ready.

**Jenkinsfile.** A pipeline definition written in Groovy that lives in the
repository. Jenkins reads it on every build, so the pipeline is versioned
alongside the code instead of clicked together in a UI.

**Terraform state.** A file that records what infrastructure Terraform has
created. It is how Terraform knows what already exists so it only makes the
changes you asked for, nothing more. Never commit state files to Git — they
contain secrets.

## Troubleshooting

The detailed troubleshooting guide is in `Setup_Guide.md` (covers Docker
Desktop startup, VS Code kernel selection, Copilot sign-in, Jenkins service
issues, and Docker socket mounting for containerised Jenkins).

A few notebook-specific tips:

**Azure OpenAI returns an authentication error.** Check that the endpoint URL
in `.env` ends with a `/` and that `DEPLOYMENT_NAME` matches exactly what is
shown in Azure OpenAI Studio (case-sensitive).

**Docker build fails with "no space left on device".** Run
`docker system prune -f` to clear unused images and build cache, then retry.

**Pushing `lab_output/` to GitHub fails with "file size exceeds 100 MB".**
The `.terraform/` provider cache was committed by mistake. Confirm `.terraform/`
is in `.gitignore`, then rewrite history with
`git filter-repo --path .terraform --invert-paths --force` and force-push.

**Jenkins pipeline fails with `sh: not found`.** Jenkins on Windows has no
Unix shell. Replace `sh` steps in the AI-generated Jenkinsfile with `bat`
before running.
